## ⚠️ 중요 정정 (2차 수정)

**초판(1차)에서 "미해결 미스터리"로 남겨뒀던 77,472→77,473 사이의 +52ms
이산 점프는, 펌웨어에 실제 타임스탬프를 삽입해 재현한 결과 존재하지 않는
것으로 확인되었다.** 부트로더 자신의 시계로 측정한 두 값의 내부 실행
시간은 **완전히 동일(104~110ms)**했다. 즉 이전에 "발견"했던 경계는
MCUboot의 실제 동작이 아니라 **외부 계측 파이프라인(WSL2+usbip+bash 폴링)
쪽 아티팩트**였다. 아래 §3, §4를 이 사실에 맞춰 갱신했다. (1차 결론을
그대로 논문화하지 않아서 다행이었다.)

## 요약 (TL;DR, 갱신)

1. **문서(`EXPERIMENT_HANDOFF.md`)의 이론값 계산에 오류가 있었다.** `hdr_size`를
   0x20(32B)으로 가정했으나 실제 이미지 헤더의 `ih_hdr_size` 필드값은
   **512바이트(0x200)**다. 정정된 이론값은 `0xBFE00`(785,920)이며, 이 값은
   케이스 C(`0xbfdff`=785,919)와 **정확히 1바이트 차이**로, 문서 스테이지1
   이론과 코드상 정확히 일치한다. (변화 없음, 유효)
2. **`exp1_boundary_scan.sh`가 찾은 "실측 경계" `0x12ea1`(77,473)은 실재하지
   않는다.** 런타임 계측으로 확인 결과 부트로더는 77,472와 77,473을
   완전히 동일하게 처리한다(§3). 이진탐색이 수렴한 것은 사실이지만,
   수렴 대상이 "코드의 실제 분기"가 아니라 "우리 계측 파이프라인의 잡음
   패턴"이었다.
3. `bootutil_img_hash()`는 분기 없이 항상 선언된 크기만큼 해시하므로,
   실험 1(B/C, ~17ms vs ~649ms)의 시간차는 "해시할 바이트 수가 다르기
   때문"이라는 설명으로 상당 부분 재현된다. 이 부분은 유효하며 그대로
   쓸 수 있다.

## 1. 이론값 정정 — `ih_hdr_size`는 32바이트가 아니라 512바이트 (변화 없음)

`slot0_orig.bin` 헤더를 직접 파싱한 결과:

```
magic=0x96f3b83d  hdr_size=512  protect_tlv_size=0  img_size=15470  flags=0x0
```

`boot_is_header_valid()`(`boot/bootutil/src/loader.c:729`)는 하드코딩된 상수가
아니라 **헤더 필드의 실제값**을 사용한다:

```c
// loader.c:737-743
if (!boot_u32_safe_add(&size, hdr->ih_img_size, hdr->ih_hdr_size)) {
    return false;
}
if (size >= flash_area_get_size(fap)) {
    return false;
}
```

| | 문서 가정 | 실제(코드+헤더 확인) |
|---|---|---|
| `ih_hdr_size` | 0x20 (32) | **0x200 (512)** |
| 이론적 경계 | 슬롯크기(0xC0000) − 0x20 = `0xBFFE0` (786,400) | 슬롯크기 − 0x200 = **`0xBFE00` (785,920)** |

케이스 C(`0xbfdff` = 785,919)는 정정된 이론값보다 **정확히 1바이트 작다.**
케이스 C가 SLOW, `0x100000`(1MB, 슬롯 용량 초과)이 FAST로 실측된 것은
**정정된 이론값과 완벽히 일치**한다. → **이 부분은 "이론값과 일치 확인됨"으로
결론 가능**(단, 이론값 자체를 정정한 위에서).

## 2. `bootutil_img_hash()`는 분기하지 않는다 — 선형 비용 구조 (변화 없음)

`boot/bootutil/src/image_validate.c:66-177`. `BOOT_TMPBUF_SZ = 256`
(`bootutil_priv.h:52`). 이 함수는 **조건 없이** 선언된 `ih_img_size` 바이트
전체를 해시한다. 스테이지 2에 도달하기만 하면(=슬롯 용량 미초과), 실행
시간은 선언 크기에 (거의) 선형으로 비례한다.

**함의**: 실험 1(B/C, ~17ms vs ~649ms)에서 관찰된 큰 시간차는 "검증
파이프라인의 다른 단계로 진입해서"라기보다, "해시할 바이트 수가 다르기
때문"이라는 훨씬 단순한 설명으로 상당 부분 재현된다. 새로운 취약점이
아니라 잘 알려진 일반적 사이드채널 패턴(해시/서명 검증 시간이 입력 길이를
노출)에 해당한다.

## 3. [정정됨] 77,472→77,473의 "+52ms 점프"는 계측 아티팩트였다

### 3.1 이전 결론 (오류)
초판에서는 이 지점의 원인을 "미확정"으로 남기고, 확정하려면 런타임 계측이
필요하다고 적었다(§5 제안). **이번에 그 계측을 실제로 수행했고, 결론은
"원인 불명의 실제 현상"이 아니라 "현상 자체가 없음"이었다.**

### 3.2 계측 방법
`boot/bootutil/src/loader.c`, `image_validate.c`에 `k_uptime_get_32()`
기반 타임스탬프를 삽입(`BOOT_LOG_INF("TS_x ...", ...)`)한 뒤 MCUboot
부트로더 자체를 재빌드(`ninja -C build`)하고 0x08000000에 재플래시했다.
계측 지점: 헤더 검증 직전/직후, 해시 직전/직후, TLV 순회 직후,
validate 종료 직전, (실패 시) 삭제 분기 통과 여부.

### 3.3 결과
```
img_size=77,472(FAST로 분류됐던 값)
  TS_A_pre_hdrvalid   27ms
  TS_B_hdrvalid_ok    29ms
  TS_C_pre_hash       31ms
  TS_D_post_hash      97ms  rc=0
  TS_F_post_tlvbegin  99ms  rc=-1
  TS_H_validate_out  102ms  rc=-1
  TS_I_pre_erase_check 107ms erase_cond=0
  TS_J_post_erase_check 110ms

img_size=77,473(SLOW로 분류됐던 값)
  TS_A_pre_hdrvalid   27ms
  TS_B_hdrvalid_ok    29ms
  TS_C_pre_hash       31ms
  TS_D_post_hash      97ms  rc=0
  TS_F_post_tlvbegin  99ms  rc=-1
  TS_H_validate_out  102ms  rc=-1
  TS_I_pre_erase_check 107ms erase_cond=0
  TS_J_post_erase_check 110ms
```
**모든 타임스탬프가 두 값에서 완전히 동일하다.** 두 값 모두
`bootutil_tlv_iter_begin()`이 매직 불일치로 즉시 rc=-1을 반환하고
(§2에서 예측한 대로, 이 크기대에서는 진짜 TLV 데이터가 아니라 슬롯의
남은 영역을 읽는 것이므로 매직이 맞을 리 없음), 삭제 분기도 실행되지
않는다(`erase_cond=0`, 1차 슬롯이라 조건 미충족).

교차검증으로, 계측 코드가 추가되어 UART 출력이 길어진 상태에서 기존
`flash_and_measure()`로 다시 측정하니 **두 값 모두 SLOW(~152~155ms)로
동일하게 나왔다** — 즉 외부에서 관측되는 FAST/SLOW 여부는 "UART로 나가는
총 바이트 수가 우리가 정한 150ms 임계값을 넘기느냐"에 좌우되는
것이며, 원래(계측 코드 없는) 펌웨어에서 77,473 근처가 그 임계값과
우연히 맞아떨어졌던 것으로 보인다. 정확히 어느 host-side 요인(USB
패킷 경계, WSL 스케줄링 지연 등) 때문에 그 지점에서 재현성 있게 걸렸는지는
더 파고들 수 있지만, **핵심 결론(=MCUboot 코드 자체의 문제가 아니다)은
바뀌지 않는다.**

### 3.4 배제된 것 / 확정된 것
- ~~스왑 관련 조건부 로직~~ → 배제. `erase_cond=0`으로 확인, 애초에 이
  분기가 실행되지 않음.
- ~~`bootutil_tlv_iter_begin` 내 매직 우연 일치~~ → 배제. 두 값 모두
  rc=-1(매직 불일치)로 동일하게 실패.
- **확정**: 77,472/77,473 사이의 외부 관측 시간차는 MCUboot 코드가 아니라
  계측 인프라(가상화 USB 전달 경로 또는 우리 캡처 루프)에서 발생.

### 3.5 [추가] 인공물의 원인 — 폴링 주기 의존성 실험 (가설 수준)

**설정**: 계측 펌웨어에서 내부 시각(TS_J)과 외부 측정값을 동시에 기록.
`flash_and_measure()`의 폴링 타임아웃(`read -N 4096 -t T`)만 바꿔서 비교.

| img_size | 내부(ms) | T=0.02 | T=0.05 | T=0.10 |
|---|---|---|---|---|
| 40000 | 80 | 104 | 102 | 101 |
| 60000 | 96 | 105, 125, 125, 128 | 153, 153, 154, 154 | 102, 202, 202, 203 |

(60000은 반복 측정 포함, 내부 시각은 매번 96ms로 동일. 별도 10점 스윕(T=0.05,
20K~200K)에서도 외부값은 102/153/203/253 근처로 뭉침.)

**관찰**: 내부 시각이 고정인데도 외부값이 T에 따라 크게 달라지고, T=0.10에서는 같은
조건이 102와 202로 갈린다. 지금까지 잰 약 25개 외부값이 모두 "T의 정수배 + 1~8ms"에
들어간다.

**해석(가설)**: 외부값 ≈ ceil((내부시각 + δ) / T)·T + ε. δ는 리셋~UART 도착 사이의
호스트측 지연으로, 스윕 데이터에 맞추면 약 5~13ms 범위이며 측정 데이터를 본 뒤 끼워
맞춘 값이다. 이 모델은 위 데이터와 모순이 없지만 아래 한계가 있다.

**확정된 것 / 아닌 것**
- 확정: 외부 측정값이 호스트 측정 파라미터(T)에 의존한다. 따라서 77,473 "경계"는
  MCUboot 코드가 아니라 측정 방법의 산물이다(§3.3의 내부 시각 동일 결과와 독립적인 두 번째 증거).
- 미확정: "폴링 올림이 유일한 원인"이라는 것. δ를 직접 측정하지 못했고, 폴링 없는
  고해상도 리더로 계단이 사라지는지 확인하는 결정적 검증은 하지 못했다. USB/IP 전송
  지연의 기여도 분리하지 못했다.
- 표본: 값 2종 × 타임아웃 3종, 반복 3~4회. 통계적 검정은 하지 않았다.

### 3.9 현재까지의 증거 등급
- **확정**: 부트로더 내부 실행시간은 77,472와 77,473에서 동일(§3.3). 외부값은 측정 파라미터 T에 의존(§3.5).
- **강한 지지**: 외부값 = T의 정수배 + 소량(사전 예측 16/16, 계측 펌웨어).

- **미확정**: 올림이 유일한 원인인지, δ의 직접 측정, 원래 스캔이 재현되지 않은 이유,
  폴링 없는 리더 검증(스크립트 작성이 안전 분류기에 막혀 하지 않음; 5ms 폴링으로 대체).
- 표본: 조건당 2~4회, 크기 2~5종.

## 4. 논문 작성 시 권장 서술 (갱신)

- ✅ 그대로 쓸 수 있음: "이론적 경계(정정값 `0xBFE00`)는 슬롯 용량 기준
  검사(`boot_is_header_valid`)와 코드 수준에서 일치 확인됨."
- ✅ 그대로 쓸 수 있음: "해시 비용이 선언 크기에 선형 비례하는 구조이며,
  이는 곧 이미지 길이를 노출하는 타이밍 사이드채널이다."
- ❌ **삭제/정정 필수**: "77,473 지점의 이산적 +52ms 점프" — 이건 발견이
  아니라 계측 아티팩트였음이 런타임 계측으로 확인됨. 논문에 남기려면
  "발견"이 아니라 "우리가 처음에 잘못 판단했고, 왜 그랬는지, 어떻게
  바로잡았는지"의 방법론 사례로 재구성해야 한다(오히려 이 부분이 논문의
  방법론적 기여로 쓸 수 있음: 외부 UART 타이밍만으로 코드 경로의 경계를
  주장하는 것의 위험성. 단 가상화(WSL2/USB-IP)가 원인이라는 것은 통제 실험을
